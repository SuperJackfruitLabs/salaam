# Implementation scope

M0–M8 implement the Pi session service foundation, reconnectable terminals, durable approvals and managed fixture effects, child work, usage accounting, durable task facts, managed compaction and an ACP client. S1–S6 have local fixture evidence; verification records the observed platforms and acceptance runs.

## Proof boundaries

S6 is exercised by manifest rejection, including missing approval/ledger capabilities, storage failure, forged or stale worker requests, heartbeat loss, real extension-load failure, context-hook failure and nested policy failure. Real Pi also runs successful diagnostic turns and resumes a persisted conversation.

S1 now has an independent real-Pi offline proof: kill a terminal during a granted tool call, reconnect to the same worker and verify one user message, one attempt and one tool grant. Lost acceptance replies, durable event reconnects, service death during a prompt and death before completion commit have separate tests. Active attempts become interrupted after service death and are not replayed; unclaimed queued work remains accepted. Explicit continuation supplies a new instruction and preserves the interruption record.

S2 has real-Pi evidence for two concurrent nested calls, reverse-order approve/deny, duplicate/conflicting/stale decisions, two sessions, expiry, changed targets and replacement worker epochs. Unsolicited raw Pi dialog replies cannot grant an operation. Client loss preserves pending approvals; worker loss invalidates old dialogs and requires a fresh binding.

S3 uses an independent durable HTTP-over-Unix-socket fixture. Barriers cover pre-intent rollback, prepared intent without dispatch, dispatch before external acceptance, external acceptance before response/receipt commit, and receipt commit before tool return. Service and worker death preserve or reconcile one effect. Negative/unavailable lookup, receipt mismatch and opaque connectors remain unknown; conditional writes reject changed versions. Cancellation denies prepared dispatch and preserves uncertainty after dispatch. Operator resolutions are attestations, not machine verification.

S4 has local real-Pi offline evidence for parent/service death, result redelivery, explicit acknowledgment, scoped cancellation, reserved request budgets and usage source deduplication. S5 forces three real Pi compactions and an idle worker restart, inspects the outgoing payload, retrieves old evidence, verifies failed/cancelled compaction, preserves outstanding children/unknown operations and reconciles worker death before/after Pi persistence. The scripted trace selects only outstanding work; this is structural context evidence, not a live-model behavior guarantee. ACP fixtures prove full-load/resume differences, reverse bound permissions, cancellation and recovery after client loss or a lost acceptance reply. Claude routing is implemented behind serialized-payload admission and tested against a local Anthropic-compatible fixture. One real Claude text completion and operator attachment to the running session have also been verified. No deployment, live fleet integration, broad credential compatibility, exactly-once effect for arbitrary services or production-isolation claim follows from these local tests.

Reproduce validation with `npm ci --ignore-scripts`, `npm run check`, `npm test`, `npm run verify:pi`, `npm run demo:session`, `npm run demo:managed`, `npm run demo:children`, `npm run demo:acceptance` and `npm run test:acceptance`. See `verification.md` for the last local evidence record. The acceptance runner defaults to 20 repetitions of all six proof suites. A shorter `--repeats` run is labelled partial. CI runs the same acceptance on macOS and Linux and retains JSON/log artifacts; only observed job results count as platform evidence. This completes the planned local session-service slice, not a production deployment or a general-purpose coding-tool suite. Further milestones remain undecided.

The [observed acceptance run](https://github.com/SuperJackfruitLabs/salaam/actions/runs/39036223669) passed on macOS arm64 and Linux x64 at implementation commit `9c49f74`: 123 regression tests, 1,200 repeated proof cases and all four demos on each platform. See [verification](verification.md) for source/bundle identity and the retained artifact record.

## Proposed next set: useful coding in the terminal and on a remote host

Planning date: 2026-10-17. The operator selected **develop both together**: a terminal-first personal coding experience and unattended remote operation share equal product priority. M9–M12 below are proposed implementation scope; they have not started. No delivery dates are assigned before the execution-boundary spike.

The release goal is concrete: start a repository task through `sal`, let the same task continue on an execution host after disconnecting, inspect the diff and actual verification results, answer any approval remotely, and return to an accurate final outcome. A proper TUI is part of this set.

The current baseline has a durable service, but its reachable tools are probes, fixture effects, history and read-only child controls. It still needs real file/search/edit/command tools, a full TUI, task-level verification and unattended job orchestration. M9 supplies the tools that the M10 interface will operate. Both clients continue to use the existing session service.

### M9: make the service capable of real coding

Use the managed bridge and ledger for new coding tools. Their authority, workspace identity and execution profile must be declared before readiness; enabling Pi's builtins cannot bypass those controls.

1. **M9.1 — Execution-boundary spike.** Select a supported backend and write down its threat model, filesystem/network/environment policy and process-lifetime contract. A broker-managed Linux container is the initial candidate; macOS needs a validated local VM/container path or a remote executor. This is a decision gate, not an assertion that a sandbox already exists. Keep provider credentials, the operator/bridge sockets, journal, home directories and the container-control socket outside the command environment. Restrict mounts and runtime provisioning to the trusted broker. The [Docker security documentation](https://docs.docker.com/engine/security/) identifies daemon access, mount configuration and kernel controls as distinct considerations; a process group alone supplies supervision rather than that boundary.
2. **M9.2 — Workspace and file tools.** Register an owned workspace with an immutable identity and revision. Supply bounded file listing, text search, line-referenced reads and precise patches with expected-content hashes. Check traversal, symlink escapes, changed targets and concurrent human edits. A crash after a patch but before its receipt is reconciled from actual file content; a conflicting or partial result stays explicit. Protect repository/control metadata from model-written configuration and hooks.
3. **M9.3 — Durable command execution.** Start commands under stable run IDs; expose status, bounded output pages/offsets, exit outcome and cancellation. Capture command, cwd, environment profile and workspace revision. Bound runtime, process count and output. Supervise owned process groups and preserve command identity/output across client loss. Reconcile a surviving run through the selected backend, or report interruption/unknown outcome; arbitrary commands are never blindly replayed. The [Node child-process API](https://nodejs.org/download/release/v26.7.0/docs/api/child_process.html) is a process-control reference, not a workspace isolation claim.
4. **M9.4 — Coding acceptance portfolio.** Start with ten versioned repository tasks: discovery, precise edits, a multi-file fix, test failure/repair and conflict handling. Use deterministic fixtures/hidden assertions for correctness and a small separately budgeted Claude evaluation. Record model/configuration, repository digest, actual diff, checks, tool outcomes, usage and interventions. Compare the applicable tasks with plain Pi under the same model/tools/budget where possible. Select backend/dependency versions only after this spike; existing Node/Pi pins remain explicit inputs.

The paired demonstration submits a code change from the terminal, disconnects during a long-running command, reconnects through the remote path and observes the same command and patch results. Negative cases cover credential/control-socket access, filesystem escape, missing backend, nested/child bypass, disk-full recording failure and cancellation of owned descendants. Readiness may advertise execution only for the backend/profile actually verified.

### M10: make both operator paths usable

The TUI is an operator client of the service. First evaluate the pinned Pi terminal component exports for reuse; choose and pin the rendering library after a small PTY spike. Keep the Pi RPC worker and the user interface in separate lifetimes.

- In a TTY, bare `sal` opens create/pick/resume. Retain explicit scriptable CLI commands. Support a multiline editor, paste, input history and visible keyboard help.
- Render Markdown, tool progress with nesting, command logs, diffs and artifacts. Reconcile volatile streaming previews with committed message identities so reconnect does not duplicate text or present a preview as a completed result.
- Present operation-bound approval cards with the reviewed target, arguments and revision; distinguish detach, cancel work and stop service. Display controller ownership, takeover, reconnect state, workspace/executor identity and known/estimated/unknown usage.
- Use SSH to reach the same host-local service initially. Exercise a real remote host rather than treating a second local process as SSH evidence. Keep ACP behavior aligned with service truth and rehearse one named editor integration.

Exit tests cover actual PTY input/resize/Unicode/paste, terminal restoration, slow output, network loss, takeover and concurrent approvals. Both terminals must show the same session/attempt/workspace identities and final diff. One successful coding task is rehearsed on each supported client/backend combination before advertising it.

### M11: make unattended completion trustworthy

Add durable task and step identities above execution attempts. Record explicit transitions such as accepted, running, waiting for a person/child/infrastructure, verifying, succeeded, failed, blocked, partially completed and cancelled. An attempt settling is evidence for a task transition, not the task transition itself.

- Bind the objective, constraints, plan/step revisions, dependencies and acceptance checks to the task. Preserve corrections and completed work across attempts and worker replacement. Present that same plan in the TUI and remote inspection API.
- Persist verification evidence with the exact workspace/diff digest, command, environment, exit outcome and artifact references. Recheck the digest before accepting verification; a subsequent edit makes an earlier passing result stale. Final completion requires the configured checks and deliverable evidence, with an explicit operator exception where verification is unavailable.
- Enforce task-wide request/runtime/concurrency limits and declared token bounds across parent/children/verification. Track estimated spending separately from provider billing. Preserve reservations for uncertain usage; reaching a limit pauses or blocks work with a durable reason.
- Create task-owned checkpoints and compare-before-restore operations. Preserve pre-existing dirty work and newer human edits. Expose a conflict or partial restoration instead of overwriting unrelated changes. Never infer that a checkpoint rolls back external effects.
- Allow managed deterministic compaction between bounded idle task steps, with the existing grant/receipt rules. A context-capacity failure remains explicit. Model-generated compaction requires a separately admitted and accounted design before it is enabled.

The paired proof starts a task in the TUI, lets its steps execute unattended, kills a worker/service between steps and reviews the resumed result remotely. Inject a false model completion, failing tests, a stale passing receipt, budget exhaustion and a human edit after checkpoint creation. A task must not report success from any of those conditions without the required fresh evidence or recorded exception.

### M12: run bounded jobs unattended on a real remote host

Introduce durable job definitions and occurrences that refer to task/workspace/profile identities. A schedule occurrence, task, session, attempt, worker and external operation retain separate IDs.

- Support explicit one-shot jobs and persisted schedules with timezone/DST semantics, occurrence deduplication and an explicit skip/bounded-catch-up policy. Default to one active occurrence per job; supersession/overlap must be configured and recorded. Service restart must not turn one missed interval into uncontrolled duplicate tasks.
- Start with SSH-invoked job controls and the trusted host-local operator boundary. Bind any trigger to an existing permitted job definition and stable logical request; caller-supplied metadata cannot widen its workspace/tool authority or answer a human approval. A public trigger gateway or new cross-product protocol needs a separately specified authentication/contract change before exposure.
- Record remote-host bootstrap, exact build/runtime/backend/provider configuration, daemon supervision and health/recovery behavior. Keep provider keys outside workspaces and execution environments. Surface waiting approvals, blocked infrastructure, uncertain effects, results and verification in a durable operator inbox shared by the TUI and CLI/ACP.
- Pilot with one macOS operator client and one Linux execution host. Reconnect from a second device, review a real approval, inspect a checked diff and resume after a controlled daemon restart. Record the actual SSH/editor/host observations and their supported capability matrix.

Exit proofs cover duplicate and changed triggers, overlap, downtime/catch-up, DST boundaries, unavailable hosts, expired approvals, cancellation, disk-full recording failure and crash around job acceptance. A failed or ambiguous effect stays governed by S3; a scheduler cannot grant itself an approval or blindly resubmit an interrupted command.

### Acceptance and sequencing

Deliver in order **M9 → M10 → M11 → M12**, with small reviewable slices inside each milestone. Preserve S1–S6 as regression gates and add independent coding/execution/TUI/task/job proofs. Repeat the new named crash boundaries in the acceptance bundle and retain source/build/backend/platform identity. Offline fixtures remain the default; live Claude and real remote-host evaluations have explicit budgets and separate reports.

The first gate is M9.1: the selected backend must pass the credential/control and workspace-boundary probes before arbitrary repository commands become available. The first daily-use gate is M9–M10: both local and remote clients can perform and review a real coding task. The unattended-release gate is M11–M12: a bounded remote job reaches a verifiable outcome across disconnect/restart, with required human decisions preserved.

The only setup decisions needed when implementation reaches them are the supported execution backend, a disposable repository task portfolio, one permitted SSH execution host and a target ACP editor. These are implementation inputs, not reasons to invent a deployment during planning.

Write-capable parallel children/worktrees, broader scoped memory/semantic compaction, dynamic skill/MCP packages, browser workflows, additional providers, automatic model routing and fleet-wide integrations remain outside this proposed set. Revisit them after measuring verified success, interventions, recovery, latency and cost on the first coding/remote pilot. Existing read-only child and explicit task-fact capabilities remain available.
